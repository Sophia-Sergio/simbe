# Linked inquiries Implementation Plan

> **For Cursor / OpenCode:** Implement task-by-task. Follow `docs/conventions/` and `docs/design/brand.md`. Stop if blocked — do not replan silently. **Commit after every task.**

**Goal:** Link the inquiries of one person (same email) without merging them: lead panel "Also inquired", import review wording and overlap warning, and `unique_candidates` next to the lead count.
**Spec:** `docs/superpowers/specs/2026-10/2026-10-19-0128-linked-inquiries-design.md` (approved)
**Depends on:** nothing unmerged · **Unblocks:** per-person metrics, a repeat-inquiry badge on cards (both non-goals here)
**Architecture:** A generated column `leads.person_key` (lower-cased, trimmed email, null when blank) identifies a person inside an agency. A small pure rule (`Leads::Overlap`) and one service (`Leads::Inquiries`) feed the lead-detail API and the importer's warnings; `Metrics::Summary` adds one distinct count. No lead is merged and no existing number changes.
**Tech Stack:** Rails 8 packs (`leads`, `ingest`, `metrics`), Postgres 16, OpenAPI contract + generated types, MSW mocks from the contract examples, React 19 + Tailwind, RSpec, Vitest, Playwright.

## Global Constraints

- A person is the lead's email, lower-cased and trimmed. A blank email is never linked (each such lead is its own person).
- `leads.person_key` is a generated **stored** column `NULLIF(lower(btrim(email)), '')` with an index on `(agency_id, person_key)`. The importer does not write it.
- Every query that groups or joins on `person_key` also filters by `agency_id` (the `Lead` default scope does this; raw SQL binds `agency_id`).
- `other_inquiries` items have exactly: `id` (the lead's `external_id`), `created_at`, `stage`, `status`, `outcome_reason`, `channel`, `campaign`, `coordinator`. Oldest first, never the lead itself, always present (empty array).
- Owner sees all of the person's other inquiries; a coordinator only those assigned to them (`Leads::Access.relation`), and never learns that others exist.
- `open_overlap` is a boolean computed over **all** of the person's leads in the agency: true when the lead is in an overlapping pair. A pair is (earlier, later) ordered by `(created_at, external_id)`; the earlier one is **closed** when its outcome is `not_eligible`, `withdrew`, `unresponsive` or `accepted` and its `outcome_updated_at` is strictly earlier than the later one's `created_at`. Otherwise the pair overlaps.
- Import review: keep the warning code `duplicate_email` and its count; its message becomes "N extra leads share an email with another lead; they are linked as one person and kept as separate inquiries". New warning code `open_duplicate_inquiry`, count = overlapping pairs, never an error.
- `kpis.unique_candidates` is an integer: distinct `person_key` among the cohort's leads, a blank-email lead counts as one. The four headline KPIs and every existing golden value are unchanged.
- Never combine or compare screener answers across inquiries. No contact details, screener data or activity in `other_inquiries`.
- Verification commands use Docker/`make`. UI is not done until seen at 1280px and 390px.

## Review Focus

- Two agencies that upload the same export: an owner never gets another agency's leads in `other_inquiries` (Task 3).
- Email with surrounding spaces or mixed case, and a blank or null email: linked correctly, or not linked at all (Tasks 1, 3).
- A person with 3 or more inquiries: every other inquiry is listed, and every overlapping pair is counted once (Tasks 2, 5).
- A coordinator whose related leads belong to someone else: `other_inquiries` is `[]`, yet `open_overlap` can still be true and reveals only that boolean (Task 3).
- Equal timestamps, and a closed outcome with a null `outcome_updated_at`: both treated as still open (so the pair overlaps), because "closed" requires a strictly earlier timestamp (Task 2).

## Task 2: Overlap rule and `Leads::Inquiries`

**Files:** Create `leads/overlap.rb`, `leads/inquiries.rb`, `spec/services/leads/inquiries_spec.rb`.
**Interfaces — Produces:**
- `Leads::Overlap::CLOSED_OUTCOMES = %w[not_eligible withdrew unresponsive accepted]`
- `Leads::Overlap.pairs(inquiries) -> Array<[earlier_id, later_id]>` where `inquiries` is an array of `{ id:, created_at:, outcome:, outcome_updated_at: }` (`Time` values, `outcome_updated_at` may be `nil`). Sorts by `[created_at, id]`; for every `i < j` emits `[sorted[i][:id], sorted[j][:id]]` unless sorted[i] is closed, meaning its outcome is in `CLOSED_OUTCOMES` and its `outcome_updated_at` is present and strictly `< sorted[j][:created_at]`. (Pure; used by the importer too.)
- `Leads::Inquiries.call(user:, lead:) -> { other_inquiries: Array<Hash>, open_overlap: Boolean }`; item keys as in Global Constraints, `status` is `Leads::Status.call(outcome: l.outcome, queue: nil)`, `stage` is `current_stage`, `coordinator` is `coordinator_name`, `created_at` is `lead_created_at`. Returns `{ other_inquiries: [], open_overlap: false }` when `lead.person_key` is nil. Visible items come from `Leads::Access.relation(user).where(person_key: lead.person_key).where.not(id: lead.id)` ordered by `lead_created_at, external_id`; `open_overlap` from `Overlap.pairs` over `Lead.where(person_key: lead.person_key)` (default scope = agency), true when `lead.external_id` appears in any pair.

- [ ] **Step 1: Failing spec** (`spec/services/leads/inquiries_spec.rb`, `build`/plain hashes for `Overlap`, Alpha for `Inquiries`). Overlap examples with exact assertions: (a) earlier `unresponsive` closed at `10:00`, later created `11:00` → `pairs == []`; (b) earlier still `open` → `[[a, b]]`; (c) three inquiries all open → 3 pairs `[[a,b],[a,c],[b,c]]`; (d) equal `created_at` is ordered by `id`; (e) earlier `accepted` with `outcome_updated_at` equal to the later `created_at` → still a pair; (f) earlier `unresponsive` with `outcome_updated_at: nil` → a pair.
